## Minimum registry and passport scope to evaluate after the llama.cpp blocker closes

This is a design boundary for a later bounded implementation, not approval to change contracts in this intake:

1. Reuse the existing Runtime Broker, Model Access, Authority, Resource Admission, and qualification owners. Do not create another runtime service or readiness state machine.
2. Keep a **strict, versioned, small profile allowlist**, not a plugin platform or arbitrary runtime string. It must distinguish runtime family from execution profile/backend so two llama.cpp builds (for example Vulkan and ROCm) cannot share qualification.
3. A qualification record needs, at minimum: stable profile ID; adapter/runtime version and executable/library build digest; accelerator/provider and version; OS/build plus native/WSL/container and process architecture; observed device/vendor/architecture/driver; exact model artifact/package hashes and source lineage; runtime-affecting context/template/parameter digest; capability claims; admission policy and sourced measurements; evidence-set digest/date/staleness rules.
4. Unknown or unavailable fields remain UNKNOWN and fail any profile match that depends on them. No wildcard matching, nearest-profile inheritance, Unsloth qualification inheritance, or silent fallback.
5. Reuse existing status vocabulary where possible: DISCOVERED → AVAILABLE → COMPATIBLE → QUALIFIED → SELECTED → RUNNING; selection remains an explicit operator action. Every conversion creates a derived artifact identity.
6. Preserve the current Unsloth passport as an immutable exact entry. Migration tests must prove the old tuple still matches and any change to runtime build, backend, host/device, artifact, or required capability invalidates only the claims that depend on that identity.
