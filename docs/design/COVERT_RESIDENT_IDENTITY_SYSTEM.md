# Covert Resident Operator Identity System

Status: design specification for review; not an implementation authorization.

Scope: presentation and UX only. This document extends the Covert Cockpit Visual Specification supplied in the design review. It does not claim that the preceding specification has been saved as a repository file.

Visual authority: the approved Covert cockpit reference, particularly its angular hood/helmet silhouette, purple illumination, cyan technical edges, and Resident-primary composition. The reference is a composite image, not a production asset pack.

## 1. Resident philosophy

Resident is the persistent visual identity of Covert's advisory interface. Its appearance can reflect a user-selected context while keeping the developer in control.

The intended experience is an intelligence interface operating alongside the developer. The representation does not claim consciousness, emotion, autonomous intent, or independent authority.

Product language:

- Covert Coder — Sovereign Development Environment.
- Local by default. Connected by choice.
- Your models. Your machine. Your workflow.
- AIDE Sovereign Workbench remains the engineering lineage.

### Governing boundaries

1. Appearance selection changes presentation only. It cannot select models, load skills, start workflows, approve operations, or change permissions.
2. A security appearance does not establish scanning, protection, monitoring, or security assurance.
3. Model identity and readiness remain separate evidence-backed labels.
4. Animation is never proof of execution, completion, effect certainty, or verification.
5. Missing, stale, or contradictory activity evidence produces neutral presentation and an explicit textual state.
6. Artwork supplements readable labels; it cannot replace errors, limitations, or verification evidence.
7. Assets load locally. Selecting an appearance never downloads artwork, calls a model/provider, or sends telemetry.

## 2. Variant definitions

Every variant retains the approved silhouette, visor geometry, dark metallic foundation, purple identity lighting, and cyan edge language. Equipment and secondary accents may differ; the Covert emblem and product identity do not.

| Variant | Visual standard | Presentation contexts | Must not imply |
| --- | --- | --- | --- |
| Engineering | Precision visor/goggles; graphite equipment; restrained drafting and instrument details; narrow cyan lighting | Coding, debugging, architecture, review | Code execution, approval, or successful repair |
| Security | Darker analyst equipment; recessed visor; compact inspection optics; subdued purple/cyan accents | Security review, audits, vulnerability analysis | Active scanning, threat detection, protection, or permission to act |
| Research | Open instrument arrangement; abstract information displays; broader low-intensity ambient light | Research, discovery, documentation | External searching, network connectivity, or validated findings |
| Creative | Refined visualization instruments; geometric display details; sparse magenta accents | UI, game, and experience design | Asset generation, rendering, or design approval |

Security is an analyst presentation: no weapons, targeting reticles, threat counters, or automatic scanning sweeps. Research and Creative display details are abstract artwork, not fabricated analytical results.

Do not require emotional facial expressions, lip synchronization, simulated fatigue, frustration, or celebration. The shared helmet/hood geometry provides continuity across variants.

### Selection policy

The selector is labeled **Resident appearance**, separate from model selection and operational controls.

- **Manual** is the default: Engineering initially, then the operator's selected approved appearance.
- **Follow workspace context** is optional and explicitly enabled. It may follow only an existing trusted application context source; it changes appearance alone.
- Manual selection suspends automatic following until the operator re-enables it.
- Prompt wording, model output, plugin instructions, filenames, and document content cannot establish trusted context.
- If the context source is unavailable, retain the manual appearance. Do not infer a workflow or introduce a new backend classifier.
- Defer automatic appearance changes while typing or interacting with approval/confirmation controls.
- Missing variant artwork preserves the current approved image and visibly marks the requested appearance unavailable.

A Security appearance may be idle or unavailable. An Engineering appearance may accompany a research request. Appearance and activity are independent.

## 3. Visual language and placement

### Placements

- **Environmental operator:** approved illustration beside the central Resident workspace, behind functional content and noninteractive.
- **Identity portrait:** matching small portrait beside the Resident name, project context, and textual advisory status.
- **Appearance control:** keyboard-accessible presentation selector, with an option to hide decorative operator artwork.

Both images represent the same selected identity, not two agents. Hiding artwork leaves identity text, status, and all working controls available. Switching variants preserves dimensions, scroll position, draft content, and keyboard focus.

### Materials and lighting

| Role | Treatment |
| --- | --- |
| Foundation | Near-black/navy panels and dark graphite/metallic artwork |
| Persistent identity | Low-intensity purple illumination, including idle |
| Technical detail | Sparse cyan/electric-blue edges |
| Creative accent | Restrained magenta within the shared palette |
| Attention | Amber attached to an actual advisory or degraded-state label |
| Failure | Red attached to an actual failure label |
| Positive evidence | Green reserved for the relevant evidence-backed status surface; no general verified character aura |

No authorized, verified, or secure avatar skin exists. Decorative light cannot stand in for authority or a Veritas verdict.

Use the cockpit's existing typography and panel geometry. Artwork does not cross controls, reduce text contrast, or create new dashboard panels. Decorative maps show no purported live activity or external connections.

## 4. Eye and visor behavior

Keep three inputs distinct: selected appearance, local interface interaction, and current trusted runtime observations.

| Condition | Permitted presentation | Truth requirement |
| --- | --- | --- |
| Idle | Static pose; low purple identity light | Existing supported idle/advisory label; no processing indicator |
| Pointer/focus interaction | Optional small orientation response and brief visor emphasis | Interface feedback only; no listening/activity claim |
| Request submitted, provider activity unproven | Ordinary pending indicator beside the request; neutral portrait | Waiting for response; do not imply execution |
| Current response generation proven | Small orientation toward an abstract internal display; restrained cyan emphasis | Generating response for the actual scoped request |
| Current tool operation proven | Small status accent accompanying the existing operation label | Preserve exact operation identity and state |
| Advisory attention required | Static portrait and amber indicator | Preserve advisory wording; attention does not mean blocked execution |
| Dependency unavailable | Neutral static pose; selected artwork may remain | Show each unavailable/degraded dependency independently |
| Evidence stale, mismatched, or conflicting | Stop activity-specific motion | Unknown/stale/unresolved according to the owning surface |
| Trusted terminal observation | Return to neutral after updating the relevant label | Outcome stays in evidence surfaces; no automatic success celebration |

Do not use "thinking" as a claim about model internals. Do not show microphone listening without a real supported active microphone session.

Optional local pointer response is confined to the Resident region, limited to approximately 3 degrees or 4 CSS pixels, and disabled for touch-only input and reduced motion. It is not camera-based gaze tracking. No camera, biometrics, attention analytics, or pointer-history storage is introduced.

### Scope, freshness, and ordering

Activity may use only existing trusted frontend projections. Preserve supplied request/revision/workspace and operation/admission correlation. Do not fabricate missing identifiers or sequence numbers.

A late observation for another scope or earlier operation cannot animate the current request. If existing contracts cannot establish freshness or ordering, keep neutral/unknown presentation. Time elapsed, model text, and arbitrary event arrival order are insufficient.

An authority-consumption receipt without executor entry cannot establish provider activity. Unknown dispatch or effect status must not become a completed/verified pose. Visual-subsystem failure must leave textual status and existing controls functional.

## 5. Transition rules

Appearance transitions express a configuration change.

- Standard transition: 180–300ms crossfade, with a small approved visor/light change.
- Fixed framing, pose anchor, and layout dimensions across variants.
- No cartoon morphing, elaborate armor assembly, or equipment crossing the workspace.
- Selection feedback is immediate; input never waits for the transition.
- Load the selected local asset before replacing the current one. Failure retains the existing image and reports appearance unavailability.
- Rapid selections coalesce to the latest selection; no animation queue.
- No focus capture, modal overlay, sound, or workflow delay.
- Reduced motion uses an immediate static image change with the same labels, framing, and selected-control outline.

## 6. Arrival and jetpack concept

Jetpack landing is not part of the default or required system. A helmet/visor activation or controlled lighting crossfade provides the preferred configuration-change feedback.

An approved cinematic entrance may be evaluated later under all of these conditions:

- Off by default and explicitly enabled.
- Triggered only by deliberate preview or appearance selection; never first paint, polling, reconnect, navigation, or a runtime event.
- Maximum 800ms, immediately skippable and silent by default.
- Confined to the artwork region; no camera shake, flashes, smoke, particles, or limbs over controls.
- No blocked input or confirmation controls; defer during typing/approval interaction.
- At most one sequence per deliberate selection; rapid changes cancel the previous sequence.
- Disabled under reduced motion; unavailable assets fall back to static identity.
- Requires a documented user-feedback purpose and measured target-device performance.

Walking, landing, and jetpack sequences are optional future candidates, not required assets or public-demo dependencies.

## 7. Motion guidelines and interaction plan

| Interaction | Purpose | Timing | Reduced-motion equivalent |
| --- | --- | --- | --- |
| Appearance selection | Confirm selection while preserving identity continuity | 180–300ms ease-in-out crossfade | Immediate image replacement, persistent selected label |
| Hover/focus | Identify the appearance control | 120–180ms ease-out | Static focus outline |
| Pointer orientation | Acknowledge interaction inside Resident's region | Bounded transform response; settle within 200ms | Static pose |
| Runtime-state update | Draw attention to a genuine scoped state change | One emphasis of at most 300ms | Immediate textual state and static icon |
| Optional arrival | Confirm a deliberate configuration selection | At most 800ms | Static replacement |

Scroll choreography: none. Scrolling, deep linking, or restoring a tab must not trigger entrances or replay activity.

Performance constraints:

- Maximum two concurrent animated visual groups: identity transition and one interaction/status emphasis. Cinematic arrival replaces the identity transition; it does not add another group.
- Animate transform/opacity only; do not animate width, height, top, left, margin, or padding. Light changes may crossfade approved static layers.
- Target smooth 60fps on the specified target laptop. This is an acceptance target, not a measured claim; simplify or disable motion if it cannot be met.
- No recurring JavaScript animation timers when idle, and no continuous idle character loop.
- Pause optional motion in hidden tabs and off-screen regions.
- First paint is static, readable, and functional; artwork loading never gates the application.
- Load only the selected variant and necessary portrait; do not eagerly decode the whole library.
- No dedicated GPU renderer, continuous 3D scene, or video loop is required.
- System reduced-motion changes take effect while the application is open.

Appearance preferences may persist locally through the existing preferences mechanism; automatic context following remains explicit opt-in. Transient pointer and activity-presentation state are discarded when the surface closes and are not analytics or memory input. Restoring preferences never restores runtime activity.

## 8. Asset requirements

Logical future package layout (no assets are created by this specification):

    assets/
      resident/
        variants/
          engineering/
          security/
          research/
          creative/
        animations/
        portraits/
        environmental/
        effects/

Use the existing local frontend asset packaging mechanism when implementation is authorized. This logical layout introduces no remote asset service or new runtime architecture.

### Required artwork per offered variant

- Transparent full/three-quarter operator image with common framing and anchor.
- Matching square portrait.
- Neutral static fallback.
- Optional registered visor/light layer.
- Optional transition frames only after static artwork acceptance.

Naming: `resident-<variant>-<placement>-<pose-or-layer>-vNN.<extension>`.

Example: `resident-engineering-portrait-neutral-v01.webp`.

Variants use `engineering`, `security`, `research`, or `creative`. Placements use `operator`, `portrait`, or `environment`. Do not use authority/verification outcomes as appearance names.

Resolution targets:

- Operator master: at least 1024 × 2048 pixels, transparent, with shared safe margins and pose anchor.
- Portrait master: 1024 × 1024; suitable local runtime derivatives at 128/256/512px.
- Environment: up to 2× intended CSS display dimensions for the approved placement.
- Light layers match base dimensions and alignment exactly.
- sRGB color; alpha edges must not produce pale halos on dark surfaces.
- PNG/WebP derivatives; approved vector assets must contain no scripts, tracking, or external resources.

Do not upscale crops of the supplied phone screenshot into final assets. No replacement artwork or variants may be fabricated merely to fill the layout.

### Licensing and provenance

Each set requires a human-readable manifest with asset ID/version, creator, origin, source file, license and redistribution rights, attribution, approval record, dimensions/format, checksum, and derivative relationships. Disclose generative tooling provenance where applicable.

Checksum proves file integrity only, not rights, approval, operational authenticity, or authority. Do not introduce unlicensed characters, logos, or equipment branding.

## 9. Implementation boundary

The visual system consumes presentation preferences, existing trusted context/runtime projections, and local interaction events. It produces artwork selection, accessible control feedback, and presentation state only.

It cannot produce authority decisions, admission facts, ownership claims, H1 lifecycle changes, model assignments, verification verdicts, effect certainty, or workflow execution requests.

Workflows and skills organize behavior; models provide computation. Existing approval, Execution Authority, and Harness boundaries govern execution. Verification evaluates evidence. Appearance changes none of these responsibilities.

## 10. Implementation phases

These phases describe future scope boundaries, not assignments or authorization.

1. **Static identity:** approved Engineering artwork, portrait/environment consistency, hide-artwork option, neutral fallback, accessibility, and provenance.
2. **Variant selection:** approved additional artwork, presentation-only selector, safe local loading, and preference behavior.
3. **Interaction and activity feedback:** bounded visor/orientation response and current-scope observations; unsupported states remain neutral.
4. **Optional context following:** explicit opt-in using a proven existing context source. Absent that source, remain manual-only.
5. **Optional cinematic refinement:** only after static fidelity, accessibility, and target-device performance pass; not required for public presentation.

## 11. Acceptance criteria

### Visual identity

- [ ] Offered variants preserve approved silhouette, materials, emblem, and lighting hierarchy.
- [ ] Portrait and environmental image represent the same selected appearance.
- [ ] No control overlap, layout shift, scroll reset, draft loss, or focus loss.
- [ ] Hiding decoration leaves all functional content and identity/status text available.
- [ ] All artwork has approval and redistribution provenance.

### Truth and trust boundaries

- [ ] Appearance selection causes zero provider calls, model changes, workflow starts, authority decisions, or permission changes.
- [ ] Security appearance alone creates no scanning/protection claim.
- [ ] Pointer interaction creates no processing/listening state.
- [ ] Consumption receipt plus absent callback creates no execution animation.
- [ ] Stale, replayed, mismatched, and unknown-scope observations cannot animate a current request.
- [ ] Dependency failures remain independently visible.
- [ ] Unknown effect/dispatch never becomes success or verification through presentation.
- [ ] Model/plugin/document instructions cannot control trusted activity state.
- [ ] Visual failure leaves textual truth and existing controls usable.

### Interaction, accessibility, and performance

- [ ] Appearance controls are keyboard-accessible and labeled as presentation.
- [ ] Decorative images are hidden from assistive technology when adjacent text supplies their meaning.
- [ ] Meaningful status announcements do not repeat for light effects or appearance cycles.
- [ ] Reduced-motion behavior is complete and responds to preference changes while open.
- [ ] Optional transitions are skippable, nonblocking, and coalesce rapid selections.
- [ ] No microphone, camera, tracking, sound, or network dependency is introduced.
- [ ] Idle, hidden-tab, decode, and motion behavior meet the stated constraints on target hardware.
- [ ] Restoring appearance preferences does not restore an activity state.

### Required acceptance evidence

Real rendered captures of each offered variant; a selection/focus/reduced-motion demonstration; negative tests for missing assets and stale/untrusted observations; evidence that appearance changes leave operational state unchanged; target-device performance measurements. Label fixture demonstrations explicitly and do not publish them as live operational evidence.

## 12. Remaining inputs and decision

Before the corresponding implementation phase, supply:

1. Clean approved Engineering artwork and usage rights.
2. Separately approved/provenanced assets for each additional offered variant.
3. An existing trustworthy context source before context following is enabled.
4. Proven scope/freshness/ordering for each runtime-driven state; otherwise use neutral presentation.
5. Target-device evidence before accepting optional motion.

**Design outcome:** Resident becomes a persistent, adaptable operator-interface identity. Appearance remains separate from intelligence, execution, ownership, permission, and verification. This specification grants no implementation authority.
